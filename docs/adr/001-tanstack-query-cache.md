# ADR 001. Кэширование запросов через TanStack Query

**Статус:** принято · этап 1

## Контекст

Требования: кэширование ответов, stale-while-revalidate со stale time 5 секунд, отсутствие лишних запросов, отмена запроса при размонтировании, инвалидация только при реальном изменении данных. На этапе 3 кэш будет обновляться патчами из WebSocket без рефетча.

## Решение

Используем TanStack Query v5.

- Один query key `['org-tree', { scenario }]` на всех потребителей — одинаковые запросы дедуплицируются.
- `staleTime: 5000`: в течение 5 секунд данные отдаются из кэша без запроса; позже показываются из кэша и перепроверяются в фоне.
- `queryFn` получает `signal`; когда размонтирован последний потребитель, библиотека отменяет запрос.
- Повторы только для сетевых ошибок и 5xx (`retry` с проверкой вида ошибки); невалидный ответ не повторяется.
- Фоновая перепроверка дешёвая: условный запрос с `If-None-Match`, на 304 возвращается готовая модель (ADR 003).

## Альтернативы

- **Свой SWR-кэш на `useSyncExternalStore`.** Полный контроль и нет зависимости, но дедупликацию, отмену, повторы, gc неактивных запросов и обработку фокуса/сети пришлось бы писать и тестировать самим. Для тестового задания это больше кода и риска без выигрыша для пользователя.
- **SWR (Vercel).** Легче и тоже умеет stale-while-revalidate и сравнение данных (`compare`). Но `AbortSignal` в fetcher не передаётся, отмену при размонтировании пришлось бы писать самим. Повторы по виду ошибки и сборка мусора неактивных запросов тоже слабее.
- **Только HTTP-кэш браузера (ETag).** Не даёт состояния загрузки/ошибки, дедупликации между компонентами и точки для применения патчей.

## Последствия

- +13 КБ gzip к бандлу (весь бандл сейчас ~119 КБ gzip при лимите 200 КБ).
- Точка для патчей на этапе 3 уже есть: `queryClient.setQueryData`.
- В dev-режиме StrictMode монтирует компоненты дважды, и в Network виден отменённый первый запрос. Это ожидаемо и в production не происходит.
- Когда вкладка скрыта, библиотека приостанавливает повторы до возвращения фокуса, поэтому экран ошибки в фоновой вкладке появится позже.
