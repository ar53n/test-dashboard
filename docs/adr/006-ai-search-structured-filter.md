# ADR 006. AI-поиск: запрос на естественном языке → структурированный фильтр

**Статус:** принято · этап 4

## Контекст

- Пользователь пишет запрос вроде «команды продаж с бюджетом больше 15 млн». Из него нужно получить фильтр таблицы.
- Если AI недоступен, должен работать обычный текстовый поиск.
- Ключ провайдера нельзя отдавать в браузер.
- Ответ модели недоверенный: он может не соответствовать схеме, прийти поздно или не прийти вовсе.

## Решение

**Модель не видит метрик и не фильтрует данные.** Она получает названия дивизионов и отделов (в системном промпте), но не численность, бюджеты, эффективность и не полный массив узлов. Модель только переводит запрос в `OrgFilter` — декларативный фильтр по полям, которые уже есть на клиенте. Применяет фильтр клиент, на актуальной модели с live-обновлениями.

```ts
OrgFilter = {
  nameContains?, ancestorName?,           // подстроки, ≤ 100 символов
  levels?: (1 | 2 | 3)[],                 // без повторов
  metrics?: { field, op: 'gt'|'gte'|'lt'|'lte', value ≥ 0 }[],  // ≤ 5, для эффективности ≤ 100
  sort?: { key, dir }, limit?: 1..100,
}
```

Контракт — одна zod-схема в `shared/orgFilter.ts`: сервер проверяет ей ответ модели, клиент — ответ API.

**Сервер** (`server/src/ai/aiSearch.ts`), `POST /api/ai-search {query}`:

1. Тело ≤ 4 КБ, `query` — 1–300 символов, иначе 400/413. Без `AI_API_KEY` и `AI_MODEL` — 503 `not_configured`.
2. Лимиты платных вызовов, общие для всех клиентов: не больше `AI_MAX_CONCURRENT` (4) одновременных запросов к провайдеру и `AI_RATE_LIMIT_PER_MINUTE` (30) в минуту (token bucket). Сверх лимита — 429 `rate_limited` с `Retry-After`, провайдер не вызывается. Невалидные запросы и выключенный AI лимит не расходуют. Лимит не зависит от адреса клиента, поэтому подмена заголовков его не обходит. Справедливость между клиентами обеспечивает nginx: 10 запросов в минуту с одного IP (ADR 007).
3. Запрос в `${AI_BASE_URL}/chat/completions` с `response_format: json_schema, strict: true`. В strict-режиме все поля обязательны, поэтому «условия нет» — `null`. Системный промпт описывает иерархию и метрики, в нём перечислены названия дивизионов и отделов («в Продажах» → `ancestorName`). Цифры в промпт не передаются.
4. Таймаут 8 с (`AbortSignal.timeout`) объединён с отменой при закрытии соединения клиентом (`AbortSignal.any`): ушедший пользователь не расходует токены.
5. Ответ провайдера — недоверенный JSON: оболочка без `choices[0].message` (в том числе `null`) — 502 `invalid_model_output`. Ответ модели нормализуется (`null`, пустые строки и массивы — «нет условия», повторы уровней схлопываются) и проверяется схемой контракта. Не прошёл — 502 `invalid_model_output`.
6. Ошибка провайдера → 502 без тела ошибки: в нём могут быть детали аккаунта. Таймаут → 504.

**Клиент** (`src/features/org-table`):

- Ввод фильтрует по названию в реальном времени, как на этапе 2. AI вызывается только по Enter или кнопке «AI».
- `useQuery(['ai-search', нормализованный запрос])`, `staleTime: Infinity`, `gcTime: 30 мин`, без автоматических повторов. Повтор того же запроса (без учёта регистра и пробелов) в течение 30 минут после последнего использования не обращается к API; после перезагрузки страницы запрос уходит заново.
- Кэшируются только успешные ответы: повторная отправка того же ввода после ошибки (сеть, таймаут, 503) явно делает `refetch`, иначе ключ не меняется и запрос бы не ушёл.
- Успешный фильтр **заменяет** текстовый поиск: фраза как подстрока ничего бы не нашла. Под полем — чипы с условиями и «Сбросить». Сортировка из фильтра действует, пока пользователь не выбрал свою заголовком.
- Любое изменение ввода снимает AI-фильтр. Прежний запрос теряет наблюдателя и отменяется через `AbortSignal`, запоздавший ответ ложится в свой ключ кэша и на экран не попадает.
- 503, 429, ошибка, фильтр не по контракту или пустой фильтр → подсказка «показан поиск по названию» и текстовый поиск по введённой строке. На 429 подсказка просит попробовать позже; повторная отправка того же ввода делает новый запрос.

## Альтернативы

- **Модель фильтрует данные сама** (передать ей 80 узлов). Дороже, медленнее, результат устаревает при первом патче, и его нельзя проверить схемой. Цифры компании уходили бы провайдеру.
- **Tool calling вместо `json_schema`.** Та же гарантия формы при большем объёме кода; `json_schema` проще и поддерживается OpenAI-совместимыми серверами (vLLM, LiteLLM и др.).
- **Кэш AI-ответов на сервере.** Экономит токены между пользователями, но нужна политика инвалидации (названия подразделений в промпте). Клиентского кэша по ключу запроса достаточно для ТЗ.
- **Авторизация AI-маршрута.** Правильная защита для общего доступа, но в демо нет пользователей и сессий. Вместо неё: порт по умолчанию доступен только с этой машины, лимиты сервера и nginx ограничивают расход. При размещении в сети маршрут нужно закрыть авторизацией (SSO или basic auth на прокси) и задать бюджет у провайдера.
- **AI на каждый ввод с debounce.** Запрос к модели на каждую паузу в наборе — дорого и шумно. Явное действие (Enter) понятнее.

## Последствия

- Лимиты ограничивают расход, но не доступ: один клиент может занять общий лимит сервера, если обходит nginx или меняет IP. Остальные пользователи тогда получают 429 и текстовый поиск, но не дополнительные расходы.
- Качество разбора зависит от модели. Контракт и схема гарантируют только форму и допустимые значения, но не смысл. Смысл виден пользователю в чипах.
- В разработке AI проверен тестами с поддельным OpenAI-совместимым сервером и вручную с mock-провайдером через Docker. С реальной моделью не проверялся: ключа в окружении разработки не было.
