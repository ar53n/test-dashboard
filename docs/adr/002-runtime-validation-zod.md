# ADR 002. Валидация ответа API через zod

**Статус:** принято · этап 1

## Контекст

По требованию схема ответа валидируется на клиенте, а невалидный ответ считается ошибкой. TypeScript проверяет типы только при сборке; данные из сети он не проверяет. Дашборд показывает бюджеты и численность, поэтому показать неверные цифры хуже, чем показать ошибку.

## Решение

- Схема `orgTreeResponseSchema` на zod 4 (`src/entities/org/model/schema.ts`), `satisfies z.ZodType<OrgNode>` связывает её с типом контракта из `shared/contract.ts`: расхождение схемы и типа ломает сборку.
- Правила сверх типов: `headcount` — целое ≥ 0, `budget` ≥ 0, `performance` в 0–100, `updatedAt` — ISO 8601.
- Структурные инварианты, которые схема элемента выразить не может (уникальность id, существующие родители, отсутствие циклов), проверяет `buildIndex`. Нарушение тоже превращается в `ApiError('validation')`.
- Ответ валидируется целиком: при любой ошибке данные не попадают в кэш, экран ошибки показывает до 5 проблем.

## Альтернативы

- **Ручной type guard.** Нет зависимости, но растёт объём кода и хуже сообщения об ошибках; расхождение с типом не ловится компилятором.
- **`zod/mini`.** Меньше бандл, но менее читаемый функциональный API. Бандл укладывается в лимит с запасом, поэтому выбрана классическая версия; при нехватке бюджета замена локальна — один файл.
- **Отбрасывать только невалидные узлы.** Отброс одного узла тихо искажает суммы предков — для аналитики это хуже явной ошибки.

## Последствия

- ~15 КБ gzip к бандлу.
- Один невалидный узел блокирует отображение всего дерева — осознанный выбор в пользу корректности цифр.
- Схема переиспользуется для патчей и AI-фильтра на этапах 3–4.
