# Архитектура

## Обзор

```
┌──────────── браузер ─────────────┐        ┌────────── server/ (Node 24) ──────────┐
│ React UI (widgets, features)     │        │ http.ts   GET /api/org-tree, /health  │
│   ▲ useOrgModel()                │        │ store.ts  in-memory дерево,           │
│ TanStack Query cache             │  HTTP  │           epoch + revision            │
│   ▲ fetchOrgModel (queryFn)      │ ─────► │ data/generate.ts  детерминированный    │
│ fetch → zod → buildIndex →       │ ◄───── │           генератор (80 узлов)         │
│         computeAggregates        │        └───────────────────────────────────────┘
└──────────────────────────────────┘
```

В dev-режиме Vite проксирует `/api` на `localhost:3001` (`vite.config.ts`).

## Слои клиента

Структура в духе feature-sliced: зависимости направлены только вниз.

| Слой | Путь | Что лежит | Может импортировать |
| --- | --- | --- | --- |
| app | `src/app` | корень приложения, провайдеры (QueryClient, тема) | всё |
| widgets | `src/widgets` | компоновка страницы: `Dashboard`, split-view и вкладки, общие состояния панелей | features, entities, shared |
| features | `src/features` | пользовательские сценарии: `org-tree` (дерево, раскрытие, выбор), `org-table` (таблица, сортировка, поиск) | entities, shared |
| entities | `src/entities/org` | модель оргструктуры: схема, индекс, агрегаты, запрос, базовые UI-элементы | shared |
| shared | `src/shared` | HTTP-обёртка, ошибки, форматирование, хуки (`useDebouncedValue`, `useMediaQuery`), тема, общие UI-компоненты | — |
| contract | `shared/contract.ts` | типы и константы протокола, общие для клиента и сервера | — |

Абсолютные импорты: `@/…` → `src/…`, `@shared/…` → `shared/…` (алиасы в `vite.config.ts`, `paths` в `tsconfig.app.json`).

## Поток данных: от API до UI

1. **Компонент** вызывает `useOrgModel()` (`src/entities/org/api/orgTreeQuery.ts`). Все потребители используют один query key, поэтому запрос один на всех.
2. **TanStack Query** решает, нужен ли запрос: данные свежие 5 секунд (`staleTime`), после этого показываются из кэша и перепроверяются в фоне (stale-while-revalidate).
3. **`fetchOrgModel`** выполняет условный запрос:
   - берёт версию текущей модели из кэша и отправляет `If-None-Match: "<epoch>-<revision>"`;
   - `cache: 'no-store'` отключает HTTP-кэш браузера, иначе браузер сам превратил бы 304 в 200 и клиент не узнал бы, что данные не изменились;
   - на 304 или на ответ с той же/более старой версией возвращает модель из кэша — без разбора JSON и без агрегации.
4. **Валидация** (`schema.ts`, zod): ответ, не соответствующий контракту, превращается в `ApiError('validation')` и не попадает в кэш.
5. **Построение модели** (`orgModel.ts`): `buildIndex` проверяет целостность дерева (уникальность id, существование родителей, отсутствие циклов), `computeAggregates` один раз считает агрегаты всех узлов.
6. **Кэш** хранит готовую `OrgModel`. `structuralSharing` сравнивает версии: снимок той же или более старой ревизии не заменяет модель, поэтому нет лишних ререндеров.
7. **UI** читает модель: дерево берёт индекс, таблица — готовые агрегаты, шапка — агрегаты корней. Дерево и таблица подписаны на один query key, поэтому в split-view запрос один.

## Интерфейс: дерево и таблица

### Раскладка

- При ширине от 1280px (`media.split`) дерево и таблица стоят рядом. Страница занимает ровно экран, каждая панель прокручивается сама.
- Уже 1280px в шапке появляется переключатель «Дерево / Таблица». Рендерится только активная панель.
- Media query задана в одном месте (`src/shared/ui/media.ts`). Её используют и CSS, и `useMediaQuery`, поэтому раскладка и логика рендера переключаются на одной ширине. `useMediaQuery` построен на `useSyncExternalStore` и читает значение синхронно, так что первый рендер не «мигает».

### Где живёт состояние

```
Dashboard
├── useOrgModel()          данные (кэш TanStack Query)
├── useOrgTreeState(model) раскрытые ветви, выбранный узел
├── useOrgTableState()     строка поиска, сортировка
├── OrgTree   ← model, expanded, toggle, selection
└── OrgTable  ← model, state, selectedId, onSelect = tree.select
```

Состояние обеих панелей поднято в `Dashboard`. На узком экране неактивная панель размонтируется, а раскрытые ветви, выбор, поиск и сортировка должны сохраниться. Кроме того, таблица должна уметь выбрать узел в дереве.

- **Раскрытие.** Пока пользователь ничего не менял, множество раскрытых узлов вычисляется из индекса: глубина ≤ 1. После первого действия хранится явное множество.
- **Выбор строки** (`select(id)`):
  1. в одном обновлении состояния раскрывает всех предков узла и записывает `selection = { id, request }`;
  2. дерево в эффекте по `(id, request)` находит строку и вызывает `scrollIntoView({ block: 'nearest' })`, при `prefers-reduced-motion` без анимации.
  - `request` растёт при каждом выборе, поэтому повторный клик по той же строке снова прокручивает дерево.
  - Если дерево не на экране (вкладка «Таблица»), эффект срабатывает при его монтировании. Вкладка сама не переключается, выбранная строка подсвечивается в таблице.
- **Ререндеры.** `OrgTree` и узлы дерева обёрнуты в `memo`, а колбэки стабильны, поэтому ввод в поиск не перерисовывает дерево.

### Таблица

Производные данные мемоизированы цепочкой, и каждое звено пересчитывается только при изменении своих входов:

```
model ──buildRows──► rows ──sortRows(sort)──► sorted ──filterRows(search)──► visible
```

- `buildRows` берёт готовые агрегаты модели и ничего не суммирует. Ссылка на модель меняется только при новой версии данных (`structuralSharing`), поэтому строки строятся один раз на версию.
- Сортировка стоит до фильтра: ввод в поиск не пересортировывает строки.
- **Сортировка.** Клик по заголовку сортирует по возрастанию, двойной клик — по убыванию. Браузер доставляет двойной клик как `click, click, dblclick`, поэтому итог не зависит от предыдущего состояния: всегда убывание. С клавиатуры: Enter/Space — по возрастанию, Shift+Enter — по убыванию. `aria-sort` стоит только на активном столбце.
- **Поиск.** Применяется через 250 мс после последнего ввода (`useDebouncedValue`). Очистка поля применяется сразу. Если совпадений нет, показывается отдельное состояние «Ничего не найдено» с кнопкой сброса; оно не путается с пустым ответом API.
- **Ширины столбцов.** `table-layout: fixed` и `<colgroup>`: числовые столбцы фиксированы, всё остальное место отдаётся названию. Столбцы не «прыгают» при фильтрации и сортировке, а на этапе 3 — при обновлении значений.
- **Клавиатурная навигация по строкам** (стрелки, Home/End, Enter) — задача этапа 3. Сейчас строки выбираются мышью.

## Надёжность

| Ситуация | Поведение |
| --- | --- |
| Первая загрузка | skeleton (`LoadingState`) |
| Сеть недоступна / 5xx | 2 повтора с экспоненциальной задержкой, затем `ErrorState` с кнопкой «Повторить» |
| Соединение оборвалось после заголовков, при чтении тела | сетевая ошибка: те же повторы, что при недоступной сети |
| Невалидный JSON, ответ не по схеме или битая иерархия | `ErrorState` со списком проблем, без повторов |
| Пустой массив | `EmptyState` |
| Фоновое обновление упало, данные есть | данные остаются на экране, сверху баннер с «Повторить» |
| Размонтированы все потребители во время запроса | `AbortSignal` отменяет fetch; сервер в сценарии `slow` снимает таймер |

Демо-сценарии для проверки: `?scenario=error|empty|invalid|slow` в адресе страницы пробрасывается в API.

В dev-режиме StrictMode монтирует компоненты дважды, поэтому в Network виден отменённый первый запрос и следом успешный. В production-сборке запрос один.

## Сервер

`server/` — отдельный npm workspace без сборки: Node 24 запускает TypeScript напрямую (type stripping), поэтому код использует только стираемый синтаксис (`erasableSyntaxOnly`).

- `store.ts` — состояние в памяти. `epoch` генерируется при старте процесса, `revision` растёт при изменениях.
- `http.ts` — маршруты на `node:http`, ETag и заголовки версии, 304 на совпадающий `If-None-Match`. Некорректный адрес запроса получает 400, непредвиденная ошибка обработчика — 500; процесс в обоих случаях продолжает работать.
