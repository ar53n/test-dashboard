# Архитектура

## Обзор

```
┌──────────────── браузер ─────────────────┐          ┌────────── server/ (Node 24) ──────────┐
│ React UI (widgets, features)             │          │ http.ts   GET /api/org-tree, /health  │
│   ▲ useOrgModel()   ConnectionIndicator  │          │ live.ts   WebSocket /api/live:        │
│ TanStack Query cache ◄── setQueryData ─┐ │   HTTP   │           hello, patch, heartbeat     │
│   ▲ fetchOrgModel (queryFn)            │ │ ───────► │ store.ts  in-memory дерево,           │
│ fetch → zod → buildIndex →             │ │ ◄─────── │           epoch + revision, update()  │
│         computeAggregates              │ │          │ simulator.ts  1–3 узла каждые 1,5–4 с │
│                                        │ │    WS    │ data/generate.ts  генератор (80 узлов)│
│ LiveClient ──► SyncController ─────────┘ │ ◄─────── │                                       │
│  (сокет, backoff)  (ревизии, resync,     │          └───────────────────────────────────────┘
│                     applyPatch)          │
└──────────────────────────────────────────┘
```

В dev-режиме Vite проксирует `/api` на `localhost:3001`, включая WebSocket (`ws: true` в `vite.config.ts`).

## Слои клиента

Структура в духе feature-sliced: зависимости направлены только вниз.

| Слой | Путь | Что лежит | Может импортировать |
| --- | --- | --- | --- |
| app | `src/app` | корень приложения, провайдеры (QueryClient, тема) | всё |
| widgets | `src/widgets` | компоновка страницы: `Dashboard`, split-view и вкладки, общие состояния панелей | features, entities, shared |
| features | `src/features` | пользовательские сценарии: `org-tree` (дерево, раскрытие, выбор), `org-table` (таблица, сортировка, поиск, клавиатура), `live-updates` (WebSocket, синхронизация, индикатор) | entities, shared |
| entities | `src/entities/org` | модель оргструктуры: схема, индекс, агрегаты, `applyPatch`, запрос, базовые UI-элементы | shared |
| shared | `src/shared` | HTTP-обёртка, ошибки, форматирование, хуки (`useDebouncedValue`, `useMediaQuery`), тема, общие UI-компоненты (`Collapse`, `Flash`, состояния) | — |
| contract | `shared/contract.ts` | типы и константы протокола, общие для клиента и сервера | — |

Абсолютные импорты: `@/…` → `src/…`, `@shared/…` → `shared/…` (алиасы в `vite.config.ts`, `paths` в `tsconfig.app.json`).

## Поток данных: от API до UI

1. **Компонент** вызывает `useOrgModel()` (`src/entities/org/api/orgTreeQuery.ts`). Все потребители используют один query key, поэтому запрос один на всех.
2. **TanStack Query** решает, нужен ли запрос: данные свежие 5 секунд (`staleTime`), после этого показываются из кэша и перепроверяются в фоне (stale-while-revalidate). Пока модель поддерживается live-патчами, `staleTime` — `Infinity` (см. «Live-обновления»).
3. **`fetchOrgModel`** выполняет условный запрос:
   - берёт версию текущей модели из кэша и отправляет `If-None-Match: "<epoch>-<revision>"`;
   - `cache: 'no-store'` отключает HTTP-кэш браузера, иначе браузер сам превратил бы 304 в 200 и клиент не узнал бы, что данные не изменились;
   - на 304 или на ответ с той же/более старой версией возвращает модель из кэша — без разбора JSON и без агрегации.
4. **Валидация** (`schema.ts`, zod): ответ, не соответствующий контракту, превращается в `ApiError('validation')` и не попадает в кэш.
5. **Построение модели** (`orgModel.ts`): `buildIndex` проверяет целостность дерева (уникальность id, существование родителей, отсутствие циклов), `computeAggregates` один раз считает агрегаты всех узлов.
6. **Кэш** хранит готовую `OrgModel`. `structuralSharing` сравнивает версии: снимок той же или более старой ревизии не заменяет модель, поэтому нет лишних ререндеров.
7. **UI** читает модель: дерево берёт индекс, таблица — готовые агрегаты, шапка — агрегаты корней. Дерево и таблица подписаны на один query key, поэтому в split-view запрос один.

## Интерфейс: дерево и таблица

### Раскладка

- При ширине от 1280px (`media.split`) дерево и таблица стоят рядом. Страница занимает ровно экран, каждая панель прокручивается сама.
- Уже 1280px в шапке появляется переключатель «Дерево / Таблица». Рендерится только активная панель.
- Media query задана в одном месте (`src/shared/ui/media.ts`). Её используют и CSS, и `useMediaQuery`, поэтому раскладка и логика рендера переключаются на одной ширине. `useMediaQuery` построен на `useSyncExternalStore` и читает значение синхронно, так что первый рендер не «мигает».

### Где живёт состояние

```
Dashboard
├── useOrgModel()          данные (кэш TanStack Query)
├── useOrgTreeState(model) раскрытые ветви, выбранный узел
├── useOrgTableState()     строка поиска, сортировка
├── OrgTree   ← model, expanded, toggle, selection
└── OrgTable  ← model, state, selectedId, onSelect = tree.select
```

Состояние обеих панелей поднято в `Dashboard`. На узком экране неактивная панель размонтируется, а раскрытые ветви, выбор, поиск и сортировка должны сохраниться. Кроме того, таблица должна уметь выбрать узел в дереве.

- **Раскрытие.** Пока пользователь ничего не менял, множество раскрытых узлов вычисляется из индекса: глубина ≤ 1. После первого действия хранится явное множество.
- **Выбор строки** (`select(id)`):
  1. в одном обновлении состояния раскрывает всех предков узла и записывает `selection = { id, request }`;
  2. дерево в эффекте по `(id, request)` находит строку и вызывает `scrollIntoView({ block: 'nearest' })`, при `prefers-reduced-motion` без анимации.
  - `request` растёт при каждом выборе, поэтому повторный клик по той же строке снова прокручивает дерево.
  - Если дерево не на экране (вкладка «Таблица»), эффект срабатывает при его монтировании. Вкладка сама не переключается, выбранная строка подсвечивается в таблице.
- **Ререндеры.** `OrgTree` и узлы дерева обёрнуты в `memo`, а колбэки стабильны (индекс читается через ref), поэтому ввод в поиск и патчи не пересоздают `toggle`/`select`.
- **Анимация раскрытия** (`shared/ui/Collapse.tsx`): transition `height` от 0 до измеренного `scrollHeight`, после `transitionend` — `auto`. Закрытие: `auto` → px → 0, затем содержимое размонтируется. Если `transitionend` не пришёл (скрытая вкладка), фаза завершается по таймеру.
  - `prefers-reduced-motion`: в CSS `transition: none`, в JS измерение пропускается и состояние меняется сразу.
  - Раскрытие предков при выборе строки в таблице не анимируется: прокрутка к узлу считала бы позицию по ещё не раскрытым ветвям.

### Таблица

Производные данные мемоизированы цепочкой, и каждое звено пересчитывается только при изменении своих входов:

```
model ──buildRows──► rows ──sortRows(sort)──► sorted ──filterRows(search)──► visible
```

- `buildRows` берёт готовые агрегаты модели и ничего не суммирует. Ссылка на модель меняется только при новой версии данных (снимок или патч), поэтому строки строятся один раз на версию. Неизменённые строки берутся из прошлой версии (ADR 005), и `memo` строк пропускает их ререндер.
- Сортировка стоит до фильтра: ввод в поиск не пересортировывает строки.
- **Сортировка.** Клик по заголовку сортирует по возрастанию, двойной клик — по убыванию. Браузер доставляет двойной клик как `click, click, dblclick`, поэтому итог не зависит от предыдущего состояния: всегда убывание. С клавиатуры: Enter/Space — по возрастанию, Shift+Enter — по убыванию. `aria-sort` стоит только на активном столбце.
- **Поиск.** Применяется через 250 мс после последнего ввода (`useDebouncedValue`). Очистка поля применяется сразу. Если совпадений нет, показывается отдельное состояние «Ничего не найдено» с кнопкой сброса; оно не путается с пустым ответом API.
- **Ширины столбцов.** `table-layout: fixed` и `<colgroup>`: числовые столбцы фиксированы, всё остальное место отдаётся названию. Столбцы не «прыгают» при фильтрации, сортировке и live-обновлениях.
- **Клавиатура** — roving tabindex: Tab попадает на одну строку таблицы, ↑/↓ и Home/End двигают фокус, Enter выбирает узел в дереве.
  - Активная строка хранится по `id`, поэтому сортировка, фильтр и патчи её не сбивают. Шаг считается от строки, на которой фокус; фокус мышью делает строку активной.
  - Если активная строка пропала из выборки, активной становится ближайшая по позиции. Фокус переносится на неё, только если он был на исчезнувшей строке. Если пользователь сам увёл фокус из таблицы, в том числе кликом по нефокусируемому месту, обновления фокус не возвращают.
  - Рамка фокуса рисуется на ячейках (`box-shadow`), а не `outline` строки: ячейки с подсветкой создают свой контекст наложения и перекрыли бы outline.
- **Подсветка изменений** (`FlashCell`): при изменении показанного значения поверх фона ячейки появляется жёлтая заливка и гаснет за 1,5 с (анимация `opacity`, перезапуск через `key`). Подсвечиваются и суммарные ячейки предков. Анимация без движения, поэтому при `prefers-reduced-motion` она остаётся.

## Live-обновления

Подробно — ADR 004 (протокол, resync) и ADR 005 (пересчёт агрегатов).

```
WebSocket ─► LiveClient ──message──► SyncController ──applyPatch──► queryClient.setQueryData
               │ статус                  │ фаза                           │
               └────── useLiveOrgSync ◄──┘                      refetchQueries (resync)
                          │
                   ConnectionIndicator
```

- `useLiveOrgSync` создаёт связку при монтировании `Dashboard` и останавливает при размонтировании. `start/stop` идемпотентны, подключение откладывается на макрозадачу, поэтому двойное монтирование StrictMode не открывает лишний сокет.
- `SyncController` работает с кэшем через адаптер `SyncTarget` (`createQueryCacheTarget`), поэтому логика тестируется без сети и React.
- `setQueryData` проходит через тот же `structuralSharing`, что и HTTP-ответ: применённый патч повышает версию модели, и запоздавший снимок старше неё модель не откатит. Следующий условный запрос уходит уже с версией патча (`If-None-Match`).
- **Индикатор:**

  | Статус | Когда |
  | --- | --- |
  | «В реальном времени» | соединение открыто, модель совпадает с сервером |
  | «Синхронизация…» | запрошен снимок после разрыва ревизий или рестарта сервера |
  | «Нет связи с сервером · повтор через N с · попытка K» | ждём переподключения; отсчёт не озвучивается скринридером |
  | «Нет сети» | браузер офлайн, попытки не тратятся |
  | «Live-обновления выключены» | демо-сценарий `?scenario=…` |

## Надёжность

| Ситуация | Поведение |
| --- | --- |
| Первая загрузка | skeleton (`LoadingState`) |
| Сеть недоступна / 5xx | 2 повтора с экспоненциальной задержкой, затем `ErrorState` с кнопкой «Повторить» |
| Соединение оборвалось после заголовков, при чтении тела | сетевая ошибка: те же повторы, что при недоступной сети |
| Невалидный JSON, ответ не по схеме или битая иерархия | `ErrorState` со списком проблем, без повторов |
| Пустой массив | `EmptyState` |
| Фоновое обновление упало, данные есть | данные остаются на экране, сверху баннер с «Повторить» |
| Размонтированы все потребители во время запроса | `AbortSignal` отменяет fetch; сервер в сценарии `slow` снимает таймер |
| Сервер остановлен | индикатор «Нет связи», переподключение с растущей задержкой: случайно от половины до полного значения 1, 2, 4 … 30 с; данные на экране, работает SWR по HTTP |
| Сервер перезапущен (новый epoch) | `hello` с другим epoch → один запрос снимка → «В реальном времени» |
| Короткий обрыв без изменений | `hello` совпал с моделью — ни одного HTTP-запроса |
| Снимок обогнал сообщения в сокете | `hello`/`heartbeat` старше модели считаются синхронными, отстающие патчи отбрасываются — без повторного запроса |
| Пропущен патч (разрыв ревизий) | resync одним запросом; патчи, пришедшие во время запроса, применяются поверх снимка |
| Сокет «завис» без закрытия | 45 с без сообщений → клиент сам закрывает соединение и переподключается |
| Невалидное сообщение WebSocket | пропускается с предупреждением в консоли; если это был патч, разрыв ревизий вызовет resync |

Демо-сценарии для проверки: `?scenario=error|empty|invalid|slow` в адресе страницы пробрасывается в API.

В dev-режиме StrictMode монтирует компоненты дважды, поэтому в Network виден отменённый первый запрос и следом успешный. В production-сборке запрос один.

## Сервер

`server/` — отдельный npm workspace без сборки: Node 24 запускает TypeScript напрямую (type stripping), поэтому код использует только стираемый синтаксис (`erasableSyntaxOnly`).

- `store.ts` — состояние в памяти. `epoch` генерируется при старте процесса. `update()` применяет изменения одной ревизией, оставляет в патче только реально изменившиеся поля и рассылает патч подписчикам.
- `simulator.ts` — каждые `SIM_MIN_INTERVAL_MS`–`SIM_MAX_INTERVAL_MS` (по умолчанию 1,5–4 с) меняет 1–3 узла: численность ±1–2, бюджет ±5%, эффективность ±5 с ограничением 0–100.
- `live.ts` — WebSocket `/api/live` на том же HTTP-сервере (`ws`, `noServer`). Upgrade на другой путь получает 404. Heartbeat каждые 15 с. Ping/pong протокола закрывает соединения клиентов, пропавших без закрытия сокета. Клиент, не успевающий читать (буфер > 1 МБ), отключается: он переподключится и сделает resync.
- `http.ts` — маршруты на `node:http`, ETag и заголовки версии, 304 на совпадающий `If-None-Match`. Некорректный адрес запроса получает 400, непредвиденная ошибка обработчика — 500; процесс в обоих случаях продолжает работать.
